# SmileRider 기획

> 고개를 기울여 조향하고, "아!" 하며 드리프트하고, 씩 웃으면 부스트하는 3D 카트 레이싱 웹 게임

> **2026-10-22 조작 변경:** 직접 플레이해 보니 윙크 조향은 눈 크기 개인차와 반대쪽 눈이 같이 감기는 문제로 좌우가 의도와 다르게 움직이는 경우가 많았습니다. 그래서 조작을 3장처럼 바꾸고 이름도 **WinkRider → SmileRider**로 바꿨습니다. 이 문서에서 윙크, 엄지 척, 주먹, 입 벌려 가속을 전제로 쓴 부분은 3장이 우선합니다.

이 문서는 지금까지 논의한 기획 내용을 정리한 것입니다. 항목마다 **확정**, **보류**(나중에 다시 결정), **논의 중**, **미정**을 구분해 표시했습니다.

## 1. 목적

- **확정** 친구들에게 링크로 공유하고 홍보하는 것이 가장 큰 목적입니다.
- 그래서 완성도, 공유 기능, "플레이하는 얼굴이 웃긴 장면"이 남는 것을 중요하게 봅니다.

## 2. 컨셉

- **확정** 카트라이더 같은 자유 조향 레이싱 게임입니다.
- **확정** 키보드 대신 웹캠으로 고개 자세와 표정을 인식해 조작합니다. 손과 눈은 쓰지 않습니다.
- **확정** 화면은 카트 뒤에서 따라가는 **3D 추격 시점**입니다.

## 3. 조작

| 조작 | 입력 | 인식 방법 | 상태 |
|---|---|---|---|
| 좌우 조향 | **고개 기울이기** | FaceLandmarker 얼굴 변환 행렬(`outputFacialTransformationMatrixes`)의 Z축 회전 | 확정 (2026-10-22 변경) |
| 엑셀 | **자동 가속** | 입력 없음. 항상 엑셀을 끝까지 밟은 상태 | 확정 (2026-10-22 변경) |
| 드리프트 | **입 크게 벌리기** ("아!") | FaceLandmarker 표정 수치 `jawOpen` | 확정 (2026-10-22 변경) |
| 부스트 | **씩 웃기** | FaceLandmarker 표정 수치 `mouthSmileLeft`, `mouthSmileRight`의 평균 | 확정 (2026-10-22 변경) |

### 이렇게 바꾼 이유

- **눈을 쓰지 않습니다.** 윙크는 눈 크기, 안경, 시선에 따라 값이 크게 흔들리고, 윙크할 때 반대쪽 눈도 같이 감겨 조향이 의도와 다르게 움직였습니다(실제 플레이 결과).
- **손을 쓰지 않습니다.** 팔 피로, 손이 얼굴을 가리는 문제가 사라지고, 손동작 모델(8.4MB, 프레임마다 약 10ms)도 필요 없습니다.
- **엑셀은 자동입니다.** 2분 내내 입을 벌리고 있는 피로가 없고, 스카이웨이는 엑셀을 끝까지 밟고도 달릴 수 있는 트랙입니다(자동 주행 한 바퀴 약 53초). 속도 조절은 드리프트(감속)와 부스트(가속)가 맡고, 실력 차이는 조향 정확도와 드리프트·부스트 타이밍에서 납니다.
- **계속하는 조작(조향)은 자세로, 잠깐 하는 조작(드리프트, 부스트)은 표정으로** 나눴습니다. 드리프트는 커브에서만, 부스트는 한 번만 하므로 표정이어도 피곤하지 않습니다.
- **반응이 빠릅니다.** 웃음은 평소(0.00)와 웃을 때(0.72 이상)의 차이가 커서 2프레임 확인으로 충분하고, 측정에서 67~100ms 만에 반응했습니다.
- 검토 후 뺀 후보: 윙크 부스트(윙크를 못 하는 사람, 깜빡임 구분), 눈썹 올리기(입을 크게 벌리면 같이 올라감), 입술 내밀기(느림), 두 눈 꼭 감기(0.5초 동안 화면이 안 보임), 몸 숙여 가속(2분 내내 숙여야 함).

### 판정 규칙 (확정)

- **조향:** 고개 기울기에 비례하는 아날로그 조향입니다. 데드존 5° 미만은 0, 25°에서 최대입니다. 보정 단계에서 "왼쪽으로 기울이기"로 방향(`tiltSign`)을 확인합니다.
- **드리프트:** 입 벌림(보정값)이 기준 이상인 상태가 2프레임 연속이면 드리프트를 시작하고, 기준 아래로 내려가면 끝납니다.
- **부스트:** 드리프트 중이 아닐 때, 웃음(보정값)이 기준 이상인 상태가 2프레임 연속이면 **한 번** 발동합니다. 웃음이 해제 기준 아래로 내려가야 다음 부스트가 준비됩니다. 웃으면서는 입을 크게 벌리기 어려워(측정: 웃을 때 입 벌림 최대 0.13) 드리프트와 부스트가 동시에 판정될 일은 거의 없습니다.
- **보정:** 게임 화면을 보면서 평소 얼굴 3초 → 고개 왼쪽으로 기울이기(방향 확인) → 입 크게 벌리기(최대 값) → 씩 웃기(최대 값). 입 벌림과 웃음은 사람마다 `(측정값 - 평소 값) / (최대 값 - 평소 값)`으로 0~1로 맞춰 판정합니다.
- 수치(3.1절)는 출발점이며, 플레이하며 `packages/controls/src/config.ts`에서 조정합니다.

### 3.1 조작 수치 초기값 (2026-10-22 측정 기반)

| 항목 | 초기값 (보정값 기준) | 측정 기준 원값으로 환산 | 측정 근거 (한 사람, 한 조명) |
|---|---|---|---|
| 조향 데드존 / 최대 | 5° / 25° (각도라 보정 없음) | | 평소 흔들림 ±0.3°, 편하게 기울일 때 최대 ±30° |
| 드리프트 시작·유지 (입 벌림) | 0.4 이상 | 약 0.35 | 평소 0.04, 말할 때 최대 0.20, "아!" 최대 0.79 |
| 부스트 발동 (웃음) | 0.6 이상 | 약 0.5 | 평소 0.00, 웃을 때 0.72~0.83 |
| 부스트 재준비 (웃음) | 0.45 미만 | 약 0.35 | |
| 확인 프레임 | 2 | | 웃음 반응 67~100ms, 말하기·평소 표정에서 오인식 0회 |

측정은 `jawGate`(웃음 판정을 막는 입 벌림 기준) 0.25에서 "아!"와 웃음을 이어 할 때 부스트가 300ms 늦게 나왔습니다. 그래서 웃음 판정을 막는 기준은 드리프트 기준과 같게(보정값 0.4) 둡니다. 드리프트 중이 아니면 웃음을 바로 인정한다는 뜻입니다.

## 4. 게임 규칙

- **확정** 카트라이더처럼 **드리프트를 하면 부스트 게이지가 차고, 씩 웃어서 게이지를 써서 부스트**합니다. "아!" 하며 커브를 돌고, 입을 다물며 씩 웃으면 튀어 나가는 흐름입니다.
- **확정** MVP는 트랙 1개에서 랩 타임을 겨루는 **타임어택**입니다.

### 첫 트랙: 빌리지 고가의 질주 오마주 (확정)

카트라이더의 **빌리지 고가의 질주**에서 구간 흐름만 가져온 오마주 트랙을 만듭니다. 원본을 그대로 재현하지 않습니다(9장의 넥슨 트랙 디자인 미사용 원칙).

- **가져올 것 (게임 디자인 아이디어):** 출발 후 부스터 모으기 → **긴 고가 직선** → 커브 → **급경사 내리막에서의 드리프트**
- **직접 만들 것:** 실제 코스 배치, 배경, 건물, 트랙 이름 (트랙 이름은 **스카이웨이**, `id: 'skyway'`)
- **길이:** 한 바퀴에 1분 안팎을 목표로 합니다. 원본은 2바퀴에 프로게이머 기준으로도 1분 40초가 넘어서, 얼굴로 조작하며 달리기에는 너무 깁니다.
- **빼는 것:** 점프대(원본에도 없음), 원본의 "인도빌드"처럼 도로 밖 지형에 올라타는 요소. 얼굴 조작으로는 그런 정밀 조작이 어렵습니다.

## 5. 공유

공유 기능은 **출시 후에 결정**합니다. 아래는 검토했던 안입니다.

- **보류** 최고 속도를 낸 순간이나 충돌한 순간의 얼굴을 찍어 **결과 카드**에 넣고, 기록과 함께 공유합니다.
- **보류** 사진은 사용자가 공유 버튼을 누르기 전까지 기기 밖으로 나가지 않게 합니다.
- 홍보 포인트: 인식 모델이 브라우저에서 돌아가므로 **카메라 영상이 서버로 전송되지 않습니다.**

## 6. 범위와 로드맵 (확정)

카트라이더 전체를 한 번에 만들면 끝내기 어려우므로 단계를 나눕니다. 지금은 1단계만 설계합니다.

1. **MVP: 트랙 1개 타임어택.** 조향, 엑셀, 드리프트, 부스트, 랩 타임, 결과 카드 공유
2. 고스트(내 최고 기록과 경주), 트랙 추가 (물리 엔진 도입 검토 시작)
3. AI 상대 (늦어도 이 단계에서 물리 엔진 도입)
4. 온라인 랭킹 (이 단계부터 서버가 필요함)
5. 아이템전, 실시간 멀티플레이

### 3D 렌더링: react-three-fiber (확정)

react-three-fiber(R3F)는 Three.js를 대신하는 라이브러리가 아니라, **Three.js를 React 방식(JSX 컴포넌트)으로 쓰게 해 주는 도구**입니다.

**R3F를 고른 이유**
- 시작 화면, 보정 화면, HUD, 결과 화면을 3D 장면과 **같은 React 트리 안에서** 다룰 수 있습니다.
- 컴포넌트가 사라질 때 Three.js 객체가 자동으로 정리되어, 트랙을 바꿀 때 메모리 누수를 피하기 쉽습니다.
- 물리 엔진을 도입할 때 `@react-three/rapier`를 바로 쓸 수 있습니다.

**규칙**
- **매 프레임 바뀌는 값은 React 상태(`useState`)에 넣지 않습니다.** 카트 위치나 속도는 `useFrame` 안에서 `ref`로 Three.js 객체를 직접 바꿉니다. 상태에 넣으면 1초에 60번씩 다시 렌더링되어 게임이 버벅입니다.
- HUD처럼 React로 그리는 화면은 값을 몇 프레임에 한 번만 갱신합니다.

**로직 분리**
- **주행 로직과 인식 로직은 React와 R3F에 의존하지 않는 순수 TypeScript 패키지로 분리합니다.** R3F는 그 결과를 화면에 그리기만 합니다.
- 이렇게 하면 주행 로직을 브라우저 없이 테스트할 수 있고, "같은 입력이면 같은 결과" 테스트도 쉬워집니다.

**버전 (2026-10-22 npm 기준)**

| 패키지 | 버전 | 비고 |
|---|---|---|
| `react` | 19.3.1 | R3F 조건 때문에 **버전 고정** |
| `@react-three/fiber` | 9.8.2 | React 19 이상, 19.4 미만 필요 |
| `@react-three/drei` | 10.7.9 | fiber 9 필요 |
| `three` | 0.186.1 | |

React 19.4가 나오면 R3F가 따라 업데이트되기 전까지 맞지 않을 수 있으므로, R3F가 지원을 발표한 뒤에 함께 올립니다.

### 3D 에셋 (확정)

**트랙 도로는 에셋을 쓰지 않고 코드로 만듭니다.**
- 주행 물리가 트랙을 "3D 중심선 + 폭(리본)"으로 다루므로, 눈에 보이는 도로도 **같은 중심선 데이터로 만들어야** 화면과 충돌 판정이 정확히 맞습니다.
- 무료 레이싱 키트는 대부분 정해진 칸에 조각을 이어 붙이는 타일 방식이라 자유 곡선 트랙과 맞지 않습니다.
- 가드레일, 고가도로 교각, 차선도 중심선을 따라 코드로 배치합니다. 트랙을 바꾸면 자동으로 따라옵니다.

**카트와 배경 소품은 Kenney의 CC0 에셋을 중심으로 씁니다.**
- CC0라 출처 표기 의무가 없고 용도 제한도 없습니다.
- 같은 작가의 에셋이라 스타일이 통일됩니다.
- 부족한 것만 Poly Pizza 등에서 CC0를 우선으로 골라 채웁니다.

### 주행 물리 (확정)

카트라이더의 주행감은 현실 물리가 아니라 게임이 의도적으로 만든 것입니다. 그래서 물리 엔진 없이 직접 구현합니다.

- **트랙 표현:** 트랙을 **높이가 있는 3D 중심선 곡선 + 폭**, 즉 공중에 놓인 리본 같은 도로 한 장으로 정의합니다. 카트는 항상 이 리본 위에 붙어서 달립니다.
- **경사와 고가도로:** 카트의 높이와 기울기를 그 지점의 리본에 맞춥니다.
- **벽 충돌:** 카트가 중심선에서 폭보다 멀어졌는지로 판정합니다.
- **입체 교차 대비:** 리본 위 위치를 트랙 전체가 아니라 **직전 위치 근처에서만** 찾아, 위아래로 겹친 도로를 헷갈리지 않게 합니다.
- **랩·체크포인트:** 중심선을 따라 진행한 거리로 계산합니다.
- **같은 입력이면 같은 결과:** 고스트(로드맵 2단계)에 유리합니다.

**물리 엔진이 필요해지는 기준은 경사가 아니라 "카트가 리본을 벗어나는가"입니다.**

| 요소 | 직접 구현으로 가능한가 |
|---|---|
| 오르막·내리막, 고가도로 | 가능 |
| 입체 교차 | 가능 (직전 위치 근처 탐색) |
| 점프대 (공중에 뜸) | 어려워짐 (낙하·착지 계산 필요) |
| 리본 밖 지형 (인도, 턱, 잔디) | 어려움 |
| 장애물·카트끼리 충돌 | 직접 만들어야 함 |

#### 물리 엔진 도입 계획 (확정)

직접 구현은 MVP까지만 씁니다. **트랙이 많아지면 물리 엔진 라이브러리를 도입할 예정입니다.** 트랙마다 점프대, 도로 밖 지형, 장애물처럼 리본 하나로 표현하기 어려운 요소가 늘어날 것이기 때문입니다.

- **도입 시점:** 트랙을 추가하는 로드맵 2단계부터 검토하고, 늦어도 카트끼리 충돌이 필요한 3단계(AI 상대)에서는 도입합니다.
- **후보:** Rapier (R3F용 `@react-three/rapier`, 내부적으로 `@dimforge/rapier3d-compat` 사용)
- **도입 범위:** 충돌 판정만 맡길지, 주행까지 맡길지는 도입할 때 정합니다. 카트라이더식 드리프트 같은 주행감은 물리 엔진을 쓰더라도 직접 조절해야 할 가능성이 큽니다.

MVP부터 이 계획에 맞춰 준비합니다.

- "바닥 높이 구하기"와 "벽 충돌 판정"을 **별도 모듈로 분리**해, 물리 엔진을 도입할 때 이 부분만 바꿀 수 있게 합니다.
- 트랙 데이터는 **특정 구현에 묶이지 않는 형식**으로 정의합니다. 같은 데이터에서 지금은 리본을, 나중에는 물리 엔진용 충돌 모양을 만들 수 있게 하려는 것입니다.

### 배포: Cloudflare Pages (확정)

**첫 접속 때 받는 용량이 큰 게임입니다.** 2026-10-22 기준 실제 크기:

| 파일 | 크기 |
|---|---|
| MediaPipe WASM (`vision_wasm_internal.wasm`) | 13.5MB (전송할 때는 압축되어 더 작아짐) |
| 얼굴 모델 (`face_landmarker.task`) | 3.8MB |

손동작 모델(8.4MB)은 2026-10-22 조작 변경으로 뺐습니다. 3D 에셋까지 더해도 첫 접속에 대략 10MB 안팎입니다. 두 번째 접속부터는 브라우저 캐시를 씁니다.

**Cloudflare Pages를 고른 이유**
- 홍보가 목적이라 접속이 한꺼번에 몰릴 수 있습니다. Vercel 무료(Hobby) 플랜은 월 전송량이 100GB라 첫 접속 20MB 기준 약 5,000명이면 찹니다. Cloudflare Pages 제한 문서에는 대역폭 한도가 없었습니다.
- Vercel 무료 플랜은 **개인 비상업 용도만 허용**해서 광고를 붙이면 유료 플랜이 필요합니다. Cloudflare Pages 제한 문서에는 이런 조항이 없었습니다.
- 무료 플랜 제한: 파일 하나 최대 25MiB(위 파일 모두 들어감), 파일 2만 개, 월 빌드 500회. 브랜치별 미리보기 배포를 지원합니다.
- **확인할 것:** Cloudflare Pages의 대역폭 무제한은 공식 문구로 확인하지 못했습니다. 가입할 때 요금 페이지에서 다시 확인합니다.

**배포 방식**
- **GitHub Actions에서 Nx로 빌드하고 결과물만 `wrangler pages deploy`로 올립니다.** 모노레포 빌드 설정을 Cloudflare 쪽에 따로 맞출 필요가 없습니다.
- WASM과 모델 파일은 직접 호스팅합니다(아래 운영 시 주의할 점).
- 모델 파일은 **경로에 버전을 넣고 캐시 기간을 길게** 잡아(`_headers` 파일), 재방문자가 다시 받지 않게 합니다.

출처: [Cloudflare Pages - Limits](https://developers.cloudflare.com/pages/platform/limits/), [Vercel - Fair Use Guidelines](https://vercel.com/docs/limits/fair-use-guidelines)

### 8.1 성능 실험 결과 (2026-10-22, 확정)

본격적으로 만들기 전에, FaceLandmarker와 GestureRecognizer, 3D 장면(상자 300개)을 같이 띄워 프레임 속도를 쟀습니다. 실험 코드는 결과만 얻고 버렸습니다.

**환경:** Apple M5, Chrome 155, 120Hz 화면, 카메라 640x480 @ 30fps

**결과 (얼굴 + 손을 카메라 프레임마다 인식)**

| 실행 위치 · 인식 방식 | 렌더링 FPS | 끊김(33ms 초과) / 최악 프레임 | 인식 횟수 | 지연 (카메라 프레임 → 결과) |
|---|---|---|---|---|
| (기준) 인식 끔 | 120 | 0회 / 11.8ms | - | - |
| 메인 스레드 · GPU | 96~98 | 0~1회 / 최대 55ms | 30/초 | 16~17ms |
| **Web Worker · GPU** | **120** | **0회 / 12~13ms** | **30/초** | **20ms** |
| 메인 스레드 · CPU | 28~83 (불안정) | 5~82회 | 28~30/초 | 20~35ms |
| Web Worker · CPU | 120 | 0회 / 11ms | 15/초 (절반 건너뜀) | 35ms |

인식 한 번에 걸린 시간은 GPU 기준 얼굴 7~8ms, 손 9~11ms, CPU 기준 얼굴 약 15ms, 손 약 20ms였습니다.

**해석**
- **메인 스레드에서 인식하면** 카메라 프레임마다 인식 시간만큼 화면 그리기가 멈춥니다. 이 고사양 노트북에서도 GPU로 120fps를 지키지 못했고, CPU에서는 크게 끊겼습니다.
- **Web Worker에서 인식하면** 렌더링이 "인식 끔"과 같습니다. 지연은 약 3ms 늘지만 체감할 수 없는 수준이고, 메인 스레드가 프레임 이미지를 넘기는 비용은 0.1ms입니다.
- **CPU 대체 모드는 Worker에서도 인식이 초당 15번으로 줄어듭니다.** 한 번 인식(약 35ms)이 카메라 프레임 간격(33ms)보다 길기 때문입니다. 화면이 끊기지 않으니 메인 스레드보다 훨씬 낫습니다.

**결정 (확정)**
1. **인식은 Web Worker에서** 돌립니다. GPU를 먼저 시도하고, 실패하면 CPU로 돌립니다. Worker 안에서도 GPU 가속이 동작하는 것을 확인했습니다.
2. **새 카메라 프레임에만 인식합니다**(`requestVideoFrameCallback`). 처음 실험에서 `video.currentTime`으로 새 프레임을 판단했더니, 실시간 카메라에서는 이 값이 프레임과 상관없이 바뀌어 같은 프레임을 화면 주사율(120Hz)만큼 중복 인식했습니다.
3. **Worker가 이전 프레임을 처리 중이면 새 프레임은 건너뜁니다.** 밀린 프레임이 쌓여 지연이 커지는 것을 막기 위해서입니다.
4. **CPU 대체 모드에서는 손 인식을 격프레임으로** 돌립니다. 얼굴 인식이 초당 30번에 가깝게 유지되도록 하려는 것입니다. (2026-10-22 조작 변경으로 손 인식 자체를 뺐으므로 더 이상 해당 없음)
5. 프레임은 `createImageBitmap(video)`로 떠서 Worker에 **소유권을 넘겨(transfer)** 보내고, Worker에서 다 쓰면 `close()`합니다.

**구현할 때 필요한 우회 처리**
- **모듈 Worker에서 모델을 두 개 이상 만들 때:** MediaPipe는 모델을 만들 때마다 `self.ModuleFactory`를 지웁니다. 모듈 Worker에서는 로더의 `import`가 캐시되어 다시 실행되지 않으므로, 두 번째 모델부터 `ModuleFactory not set` 오류가 납니다. 로더(`FilesetResolver.forVisionTasks(경로, true)`가 돌려주는 `wasmLoaderPath`)를 직접 `import`해 기본 내보내기를 보관해 두고, **모델을 만들기 전마다 `self.ModuleFactory`에 다시 넣습니다.**
- **Vite 개발 서버:** WASM 경로를 `/wasm`처럼 상대 경로로 주면, Vite가 `public` 폴더 파일을 코드에서 import하는 것으로 보고 막습니다. `${self.location.origin}/wasm`처럼 **전체 주소**를 넘깁니다.
- Worker에서는 ES 모듈용 WASM 로더(`forVisionTasks`의 두 번째 인자 `true`)를 씁니다. 모듈 Worker에서는 `importScripts`를 쓸 수 없기 때문입니다.

**표정 수치 관찰**
- 눈을 뜬 상태에서도 `eyeBlinkLeft`/`Right`가 0.27~0.36으로 나왔습니다. 카메라는 화면 위에 있고 시선은 화면을 향하니, 카메라에는 눈을 내리깐 것처럼 보이기 때문으로 추정합니다. 그래서 보정은 **게임 화면을 보면서** 합니다(10.2절).
- 실제 왼쪽 눈만 감았을 때 `eyeBlinkLeft` 0.66, `eyeBlinkRight` 0.47이었습니다. **`Left`는 실제 내 왼쪽 눈**이었고(이 환경 기준), 윙크할 때 반대쪽 눈 값도 같이 오릅니다. 두 눈 값의 차이와 보정으로 판정하는 설계가 필요하다는 근거입니다.
- 주먹(`Closed_Fist`)과 엄지 척(`Thumb_Up`)은 문제없이 인식됐습니다.
- 위 눈·손 관찰은 옛 조작(윙크, 손동작) 기준 기록입니다. 이후 실제 플레이에서 윙크 조향이 불안정해 조작을 바꿨고, 새 조작의 측정은 3.1절에 있습니다.

**한계:** M5 한 대에서만 측정했습니다. 일반 노트북에서는 인식이 더 느릴 것입니다. Worker 구조에서는 그 차이가 화면 끊김이 아니라 인식 횟수 감소로 나타나므로 결정은 유효합니다. 출시 전에 다른 노트북에서 한 번 더 측정합니다.

## 10. MVP 상세 설계 (확정)

사용자가 결정을 위임한 항목입니다. 기준은 MVP에 꼭 필요한 것만 넣고, 앞에서 확정한 원칙(로직 분리, 같은 입력이면 같은 결과, 판정 규칙)과 맞물리게 하는 것입니다.

### 10.1 저장소 구조

pnpm 워크스페이스 + Nx. 패키지 범위 이름은 `@smilerider`입니다.

| 프로젝트 | 역할 | 의존 |
|---|---|---|
| `apps/game` | React + Vite + R3F 게임 앱. 화면 흐름, HUD, 3D 렌더링, MediaPipe 실행, 키보드 입력 | 아래 세 패키지 |
| `packages/controls` | 인식 결과(고개 기울기, 표정 수치)와 보정값을 받아 **조작 입력**으로 변환. 순수 TypeScript, MediaPipe 실행 코드 없음 | `kart` (조작 입력 타입만) |
| `packages/kart` | 주행 로직. "현재 상태 + 조작 입력 + 트랙 → 다음 상태"를 계산. 바닥 높이·벽 충돌 모듈 포함. 순수 TypeScript | `track` |
| `packages/track` | 트랙 데이터 형식, 오마주 트랙 데이터, 중심선 계산(진행 거리, 직전 위치 근처 탐색, 체크포인트·랩 판정). 순수 TypeScript | 없음 |

- **조작 입력**은 카메라와 키보드가 같은 형식으로 만듭니다: 조향(-1~1), 엑셀(0~1), 드리프트(켜짐/꺼짐), 부스트(켜짐/꺼짐). 주행 로직은 입력이 어디서 왔는지 모릅니다. 엑셀은 자동이므로 주행 중에는 항상 1이고, 얼굴을 놓쳤을 때만 0입니다(10.4절).
- **주행 로직은 고정 간격(초당 60번)으로 계산**하고, 화면은 그 사이를 보간해서 그립니다. 기기 성능과 관계없이 같은 입력이면 같은 결과가 나오게 하려는 것입니다.
- MediaPipe를 불러오고 실행하는 코드는 `apps/game`의 **Web Worker**에 둡니다(8.1절). 메인 스레드는 카메라 프레임을 Worker에 넘기고, 결과(고개 기울기, 표정 수치)를 받아 `packages/controls`로 조작 입력을 만듭니다. Worker는 FaceLandmarker 하나만 돌립니다(손동작 모델 없음).

### 10.2 화면 흐름

1. **시작 화면:** 게임 소개, 조작 방법, 플레이 버튼, 설정(카메라 미리보기 켜기/끄기, 소리)
2. **카메라 권한 요청**
3. **보정 겸 튜토리얼**
   - **게임 화면을 보면서** 평소 얼굴로 3초 → 고개 기울기와 각 표정 수치의 **평소 값** 측정. 실제로 플레이하는 자세와 같아야 하기 때문입니다.
   - 고개를 왼쪽으로 기울여 보게 함 → **좌우가 뒤바뀌지 않았는지 확인**(`tiltSign`). 웹캠 화면을 거울처럼 뒤집는지에 따라 부호가 다를 수 있으므로 짐작하지 않습니다.
   - 입 크게 벌리기("아!") → `jawOpen`의 **최대 값** 기록
   - 씩 웃기 → `mouthSmileLeft`, `mouthSmileRight` 평균의 **최대 값** 기록
   - 보정 후에는 표정 수치를 사람마다 0~1로 다시 맞춥니다: `보정값 = (측정값 - 평소 값) / (최대 값 - 평소 값)`을 0~1 범위로 자릅니다. 그러면 얼굴 생김새, 조명이 달라도 평소는 0, 최대는 1에 가깝게 됩니다.
   - 최대 값과 평소 값의 차이가 너무 작으면(10.9절 기준) 그 표정은 제대로 인식되지 않는 것이므로 다시 해 보게 합니다.
4. **카운트다운:** 3초. 기록은 카운트다운이 끝나는 순간부터 잽니다.
5. **주행**
6. **결과 화면:** 전체 기록, 랩별 기록, 최고 기록 여부, 다시 하기

### 10.5 키보드 조작

- 개발과 디버깅에 쓰고, **카메라가 없는 사람에게도 "키보드 모드"로 열어 둡니다.**
- 키 배치는 카트라이더와 같게 합니다: ← → 조향, Shift 드리프트, Ctrl 부스트. 엑셀은 카메라 모드와 같게 **자동**이라 ↑ 키는 없습니다.
- 브레이크와 후진은 없습니다. 카메라 조작에도 없기 때문입니다. 속도는 드리프트로 줄이고, 벽에 부딪히면 벽을 따라 미끄러집니다.
- **키보드 기록은 카메라 기록과 따로 저장하고 표시합니다.** 키보드가 훨씬 쉬워서 같은 순위에 두면 불공평합니다.

### 10.6 기록 저장

- 서버가 없으므로 브라우저 저장소(localStorage)에 저장합니다.
- 트랙별, 조작 방식(카메라 / 키보드)별로 최고 전체 기록과 최고 랩 기록을 저장합니다.
- 저장소를 쓸 수 없는 환경(사생활 보호 모드 등)에서도 게임은 정상적으로 돌아가야 합니다. 그때는 기록만 저장되지 않습니다.

Vitest를 씁니다.

| 대상 | 내용 |
|---|---|

| `game` | 키보드 모드로 시작부터 결과 화면까지 한 바퀴 도는 E2E 테스트 1개 (Playwright) |

고개·표정 인식 정확도는 자동 테스트로 확인하기 어려우므로 직접 플레이하며 확인합니다.

### 10.8 세부 규칙

- **랩 수: 2바퀴.** 원본 스피드전과 같고, 한 바퀴 1분 목표면 한 판에 2분 정도입니다. 표정 조작의 피로를 생각하면 3바퀴는 깁니다.
- **부스트:** 드리프트로 게이지가 가득 차면 부스터 1개를 얻고, **최대 2개까지 모아 둘 수 있습니다.** 씩 웃으면 1개를 씁니다. 원본처럼 "부스터 2개를 들고 고가 직선에 진입하는" 플레이가 가능하게 하려는 것입니다.
- **체크포인트:** 트랙에 체크포인트를 두고, 모든 체크포인트를 순서대로 지나야 랩으로 인정합니다.
- **역주행:** 진행 거리가 연속으로 10m 넘게 줄어들면 "역주행" 경고를 띄웁니다. 역주행으로는 체크포인트가 인정되지 않습니다.

### 10.10 언어

- **확정** 첫 출시는 **한국어만** 지원합니다.
- **확정** 이후에 여러 언어를 추가합니다.
- **준비:** 나중에 언어를 쉽게 추가할 수 있도록, 화면에 보이는 문구는 컴포넌트에 직접 쓰지 않고 **한국어 문구 파일 한 곳에 모아 둡니다.** 번역 라이브러리(react-i18next 등)는 실제로 언어를 추가할 때 도입합니다.
- **준비:** 기록 시간 같은 숫자 표시는 브라우저 기본 기능(`Intl`)으로 형식을 맞춥니다.

### 10.11 지원 환경

- **확정** 첫 출시는 **PC 브라우저만** 지원하고, 모바일은 지원하지 않습니다.
- 휴대폰으로 접속하면 "PC에서 플레이해 주세요"라고 안내합니다.
